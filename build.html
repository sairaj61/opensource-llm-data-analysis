Which approach should I use?

A weight is one stored number inside the model. The full set of those numbers is what you download. Inference means using those weights to produce text. You do not need to change the weights to ask a question.

A token is the unit the model reads and writes. It is often a piece of a word, not a whole word. The context window is the maximum number of tokens the model can look at in one request, counting your question, any notes you attached, and the answer it is writing.

A prompt is the text you send in that request. RAG (retrieval-augmented generation) means searching your own files and pasting the matching passages into the prompt. Fine-tuning means continuing training so some weights change. Pretraining means the first, huge training run that creates those weights from random numbers.

1. RAG and tool use with your own data

Run a chat model locally with Ollama. Two patterns follow. Both leave the weights unchanged.

An embedding is a list of numbers that stands for a piece of text. Texts with similar meaning get lists that point in similar directions. A vector database stores those lists and, given a new list, returns the closest stored ones. Retrieval is that search. Chunking is cutting a long document into pieces small enough to embed and to paste back into the prompt.

Basic Document RAG

What you are doing: you keep your notes on disk. At question time you search for the passages that look closest to the question, put those passages in the prompt, and ask the model to answer only from them and to name the file each passage came from.

Why: the model’s training data does not contain your private notes, and you can edit a note without training again.

When: the knowledge is text (policies, wikis, PDFs you have already turned into text) and it does not fit in one prompt, or it changes.

Mechanism, in order:

  1. Split each document into chunks. Overlap them: the next chunk starts before the previous one ends, so a sentence that sits on the cut still appears whole in one chunk.
  2. Send each chunk to an embedding model. Here that is Ollama’s nomic-embed-text (about a 2,048-token window) or bge-m3 (8,192-token window, embedding length 1,024 on the Ollama model card). Do not mix the two in one index: the lists have different lengths, and the database will reject the mix.
  3. Store each list with the original text and the filename. This example uses Chroma. FAISS is a local index library. pgvector stores the lists in PostgreSQL.
  4. Embed the question with the same model. Ask the database for the nearest chunks.
  5. Build a prompt: the question, then the chunks, each labelled with its filename. That labelling is how the answer can cite sources.

Minutes to index a handful of notes. Re-index when a file changes. No training step.

Basic Data analysis by writing SQL

What you are doing: the model never sees the whole table. It sees the column names, a few sample rows, and the question. It writes a SELECT. Your program runs that statement in DuckDB (or pandas) and shows the result.

Why: a warehouse does not fit in the context window. The model guide uses this pattern for that reason.

When: the source of truth is a table, not a paragraph. Prefer this over document RAG for “what was the total in 2024?”

Detailed Document RAG, step by step

  1. Install Ollama and pull a chat model plus an embedding model. Pick the chat tag from the install section that fits your RAM. The embedding tags below are on the Ollama library. 
    curl -fsSL https://ollama.com/install.sh | sh
ollama pull nomic-embed-text
# alternative embedding model: ollama pull bge-m3
ollama pull granite4.1:8b
  2. Install the Python packages. The chat and embed calls match the Ollama Python library and the embed API (input in, embeddings out). Ollama’s embed endpoint returns L2-normalized vectors. 
    pip install ollama chromadb
  3. Save this as rag_docs.py. It chunks plain text, stores embeddings in Chroma, retrieves three chunks, and asks the chat model to answer with filenames. The embedding class follows Chroma’s custom embedding function shape: __call__(self, input). 
    import ollama
import chromadb
from chromadb import Documents, EmbeddingFunction, Embeddings
from chromadb.utils.embedding_functions import register_embedding_function

CHAT_MODEL = "granite4.1:8b"          # swap for a model you already pulled
EMBED_MODEL = "nomic-embed-text"      # do not mix with bge-m3 in this folder
NOTES = [
    ("refunds.md", "Refunds are allowed within 30 days of delivery. After 30 days, store credit only."),
    ("shipping.md", "Standard shipping takes 3 to 5 business days. Express shipping takes 1 business day."),
    ("tax.md", "A 5 percent goods tax applies to electronics. Books are tax exempt."),
]

def chunks(text, size=800, overlap=120):
    parts = []
    start = 0
    while start < len(text):
        end = min(len(text), start + size)
        parts.append(text[start:end])
        if end == len(text):
            break
        start = end - overlap
    return parts

@register_embedding_function
class OllamaEmbedder(EmbeddingFunction):
    def __init__(self, model: str = EMBED_MODEL):
        self.model = model

    def __call__(self, input: Documents) -> Embeddings:
        response = ollama.embed(model=self.model, input=list(input))
        return response["embeddings"]

    @staticmethod
    def name() -> str:
        return "ollama-embed"

    def get_config(self):
        return {"model": self.model}

    @staticmethod
    def build_from_config(config):
        return OllamaEmbedder(config["model"])

client = chromadb.PersistentClient(path="chroma_notes")
collection = client.get_or_create_collection(
    "notes",
    embedding_function=OllamaEmbedder(),
)
ids, docs, metas = [], [], []
for name, text in NOTES:
    for i, piece in enumerate(chunks(text)):
        ids.append(f"{name}-{i}")
        docs.append(piece)
        metas.append({"source": name})
collection.upsert(ids=ids, documents=docs, metadatas=metas)

question = "How long do I have for a cash refund?"
hits = collection.query(query_texts=[question], n_results=3)
blocks = []
for doc, meta in zip(hits["documents"][0], hits["metadatas"][0]):
    blocks.append(f"[{meta['source']}]\n{doc}")
prompt = (
    "Answer using only the notes. Then list the source filenames you used.\n\n"
    + "\n\n".join(blocks)
    + "\n\nQuestion: "
    + question
)
reply = ollama.chat(model=CHAT_MODEL, messages=[{"role": "user", "content": prompt}])
print(reply.message.content)
  4. Run it with python rag_docs.py while the Ollama app is running. The first call loads the embedding model.
  5. Optional stores, if you outgrow the Chroma folder. FAISS keeps a matrix in memory. Because Ollama’s vectors are L2-normalized, inner product equals cosine similarity: 
    import faiss
import numpy as np
# vectors: embedding lists you already computed with one model
# query_vector: the embedding of the question, same model
matrix = np.asarray(vectors, dtype="float32")
index = faiss.IndexFlatIP(matrix.shape[1])
index.add(matrix)
scores, row_ids = index.search(np.asarray([query_vector], dtype="float32"), 3)

    In PostgreSQL with pgvector, <=> is cosine distance. The vector length has to match one embedding from the model you actually used. Ollama’s bge-m3 card lists length 1,024. nomic-embed-text is a different length; print len(vector) and use that number in vector(N).

    CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  source text,
  content text,
  embedding vector(1024)  -- 1024 is bge-m3 on Ollama; change N for other models
);
SELECT source, content
FROM chunks
ORDER BY embedding <=> '[...]'::vector
LIMIT 3;

Detailed SQL sandbox, step by step

  1. Install DuckDB and build a tiny database you can check by hand. 
    pip install duckdb ollama
  2. Save as sql_sandbox.py. The model call is ollama.chat, as in the chat API. The database is opened read-only for the question. The word filter is extra, and it is not a full SQL parser. 
    import duckdb
import ollama

CHAT_MODEL = "granite4.1:8b"
BANNED = {
    "insert", "update", "delete", "drop", "alter", "attach", "copy",
    "pragma", "install", "load", "export", "create", "replace", "call",
}

def only_select(sql: str) -> str:
    text = sql.strip()
    if text.startswith("```"):
        text = text.split("\n", 1)[-1]
        if text.rstrip().endswith("```"):
            text = text.rstrip()[:-3]
    text = text.strip().rstrip(";").strip()
    if ";" in text:
        raise ValueError("Only one statement is allowed.")
    first = text.split(None, 1)[0].lower()
    if first not in ("select", "with"):
        raise ValueError("Only SELECT or WITH is allowed.")
    words = set(text.lower().replace("(", " ").replace(")", " ").split())
    found = words.intersection(BANNED)
    if found:
        raise ValueError("Refusing: " + ", ".join(sorted(found)))
    return text

setup = duckdb.connect("warehouse.duckdb")
setup.execute("""
CREATE OR REPLACE TABLE orders AS
SELECT * FROM (VALUES
  (1, 'Ada', 20.0, DATE '2024-03-01'),
  (2, 'Lin', 15.5, DATE '2023-11-02'),
  (3, 'Ada', 9.0,  DATE '2024-07-19')
) t(id, customer, amount, ordered_on)
""")
setup.close()

con = duckdb.connect("warehouse.duckdb", read_only=True)
schema = con.execute("DESCRIBE orders").fetchdf().to_string(index=False)
sample = con.execute("SELECT * FROM orders LIMIT 5").fetchdf().to_string(index=False)
question = "What is the total order amount in 2024?"
prompt = f"""Write one DuckDB SELECT and nothing else.
Schema of table orders:
{schema}

Sample rows:
{sample}

Question: {question}
"""
reply = ollama.chat(model=CHAT_MODEL, messages=[{"role": "user", "content": prompt}])
sql = only_select(reply.message.content)
print(sql)
print(con.execute(sql).fetchdf())
  3. Run python sql_sandbox.py. A correct statement returns 29.0 (20.0 + 9.0). If the model adds commentary, the fence-stripper keeps the SQL; if it writes DROP or a second statement, the script stops.
  4. For a CSV you already have, point DuckDB at the file instead of VALUES: SELECT * FROM read_csv('orders.csv'). DuckDB can also query a pandas dataframe that is in scope by its variable name. Keep the same read-only rule.

How to tell if retrieval or SQL is working

  • Write 10 questions whose answers you already know, and record which file or row holds the answer. That set is a holdout: you do not use it to tweak the prompt until you have looked once.
  • For RAG, check recall: is the right chunk among the top 3? Then check the citation: does the filename the model prints match that chunk? A fluent answer that cites the wrong file is a failure.
  • For SQL, run the model’s statement and your own statement. Compare the result tables, not the spelling of the SQL.

Common mistakes

  • Chunks larger than the embedding model’s window. nomic-embed-text is about 2,048 tokens. The script uses 800 characters so an English chunk is likely to fit; that is a character budget, not a token count. A token is not a fixed number of characters.
  • One index, two embedding models.
  • Pasting a whole CSV into the chat and calling it RAG.
  • No filename on the chunk, so the answer cannot cite a source.
  • Forgetting to re-embed after you edit a note.
  • Running model-written SQL with permission to write.

2. Fine-tuning with LoRA and QLoRA

LoRA (low-rank adaptation) does not rewrite every weight. It adds small matrices beside the frozen ones and trains only those. The size of those matrices is the rank (r). QLoRA is LoRA while the frozen weights are stored in 4-bit form. Quantization means storing each weight in fewer bits. 16-bit weights become 4-bit weights, so the file and the GPU memory get smaller, and some accuracy is traded away.

An epoch is one pass through every training example. The learning rate is the step size for each update. Too large, and the numbers thrash. Too small, and they barely move. A loss is a score of how wrong the current prediction is; training tries to reduce it. A checkpoint is a saved copy of the weights at some step.

GGUF is a file format used by llama.cpp and Ollama to run a quantized model. q4_k_m is one 4-bit quantization recipe: Unsloth’s docs describe it as Q6_K for half of certain attention and feed-forward tensors and Q4_K for the rest.

Basic When to fine-tune

Prompt the model if a clear instruction plus the schema is enough. Use RAG or SQL if the missing piece is a fact that lives in a file. Fine-tune when you have many examples of a behaviour you want every time, such as “reply with one DuckDB SELECT and no prose,” and prompting still wanders.

Suggested first project: text-to-SQL on one schema you can check. The schema stays in the prompt. The fine-tune teaches the dialect and the habit of answering with SQL. It should not memorize this month’s totals.

Dataset, in plain language

Each example is one chat: a system rule, a user message that contains the schema and the question, and an assistant message that is only the SQL. Store one JSON object per line. That file is JSONL.

How many: start small enough that you can read all of them. A few dozen hand-checked pairs tell you if the idea works. A few hundred, still checked, are a reasonable next size for this narrow task. More rows do not fix wrong SQL. These counts are practical advice, not a measured threshold.

Quality: every assistant SQL must run on your database and return the result you expect. Split by question, not by duplicate wording of the same question. Put about one in five questions into the holdout and do not train on them.

Synthetic data: a stronger model may draft pairs. Then run every statement. Discard errors and wrong results. Read a sample yourself after the automatic check. Do not train on drafts you have not executed.

Detailed QLoRA script, step by step

  1. Make two JSONL files. train.jsonl is what the trainer sees. holdout.jsonl is not. One training line looks like this (put the schema you actually have in the user message): 
    {"messages":[{"role":"system","content":"You write one DuckDB SELECT and no other text."},{"role":"user","content":"Schema:\norders(id INT, customer VARCHAR, amount DOUBLE, ordered_on DATE)\n\nQuestion: total amount in 2024"},{"role":"assistant","content":"SELECT SUM(amount) AS total FROM orders WHERE ordered_on >= DATE '2024-01-01' AND ordered_on < DATE '2025-01-01';"}]}

    Write more lines for other questions on this same schema. Keep at least a handful of different questions in holdout.jsonl.

  2. Install Unsloth in a GPU environment. Follow the install cell on the Colab page for Colab, or pip install unsloth on your own CUDA machine if that import works. You also need a recent trl, transformers, and datasets, which Unsloth’s install pulls in. Log in only when you are ready to upload: hf auth login (Hub quickstart).
  3. Save train_qlora.py. It matches the current TRL Unsloth integration and SFTTrainer: FastLanguageModel.from_pretrained(..., load_in_4bit=True), get_peft_model with r=16, and SFTConfig. The trainer parameter for the tokenizer is processing_class. Older Unsloth notebooks pass tokenizer=; that name is not in the current TRL signature. The script turns each chat into a prompt and a completion so the loss is on the SQL, which is TRL’s default for that format. eos_token is set to Qwen’s end-of-turn token, as the TRL docs show for Qwen tokenizers. 
    from datasets import load_dataset
from trl import SFTConfig, SFTTrainer
from unsloth import FastLanguageModel

max_seq_length = 2048
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen2.5-7B-Instruct-unsloth-bnb-4bit",
    max_seq_length=max_seq_length,
    load_in_4bit=True,
)
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                    "gate_proj", "up_proj", "down_proj"],
    lora_alpha=16,
    lora_dropout=0,   # Unsloth documents 0 as the optimized setting
    bias="none",
    use_gradient_checkpointing="unsloth",
    random_state=3407,
)

raw = load_dataset("json", data_files={"train": "train.jsonl", "test": "holdout.jsonl"})

def to_prompt_completion(row):
    prompt = [m for m in row["messages"] if m["role"] != "assistant"]
    completion = [m for m in row["messages"] if m["role"] == "assistant"]
    return {"prompt": prompt, "completion": completion}

train_ds = raw["train"].map(to_prompt_completion, remove_columns=raw["train"].column_names)
holdout_ds = raw["test"].map(to_prompt_completion, remove_columns=raw["test"].column_names)

trainer = SFTTrainer(
    model=model,
    processing_class=tokenizer,
    train_dataset=train_ds,
    eval_dataset=holdout_ds,
    args=SFTConfig(
        output_dir="outputs",
        num_train_epochs=2,          # use 3 only if holdout SQL is still improving
        learning_rate=2e-4,
        per_device_train_batch_size=1,
        gradient_accumulation_steps=4,
        max_length=max_seq_length,
        logging_steps=10,
        eval_strategy="epoch",       # older transformers called this evaluation_strategy
        optim="adamw_8bit",
        warmup_ratio=0.03,
        lr_scheduler_type="linear",
        seed=3407,
        eos_token="<|im_end|>",
    ),
)
trainer.train()
model.save_pretrained("lora_adapter")
tokenizer.save_pretrained("lora_adapter")
  4. Run python train_qlora.py on the GPU machine. Watch two numbers. Training loss should fall. Holdout loss should not explode while training loss goes to zero. Also run the SQL test in the next step; loss alone does not tell you the query is right.
  5. Compare the untouched base model and the adapter on the holdout. Execute both SQL strings. A match of result tables is the score that matters. 
    import duckdb
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="lora_adapter",
    max_seq_length=2048,
    load_in_4bit=True,
)
FastLanguageModel.for_inference(model)

def answer(user_text):
    messages = [
        {"role": "system", "content": "You write one DuckDB SELECT and no other text."},
        {"role": "user", "content": user_text},
    ]
    inputs = tokenizer.apply_chat_template(
        messages, tokenize=True, add_generation_prompt=True, return_tensors="pt"
    ).to(model.device)
    output = model.generate(input_ids=inputs, max_new_tokens=128, use_cache=True, do_sample=False)
    return tokenizer.decode(output[0][inputs.shape[-1]:], skip_special_tokens=True)

con = duckdb.connect("warehouse.duckdb", read_only=True)
question = "Schema:\norders(id INT, customer VARCHAR, amount DOUBLE, ordered_on DATE)\n\nQuestion: total amount in 2024"
gold = "SELECT SUM(amount) AS total FROM orders WHERE ordered_on >= DATE '2024-01-01' AND ordered_on < DATE '2025-01-01'"
predicted = answer(question)
print("PREDICTED:", predicted)
print("GOLD ROWS:", con.execute(gold).fetchall())
print("PRED ROWS:", con.execute(predicted.strip().rstrip(";")).fetchall())

    Also ask the tuned model one ordinary question it used to answer (“What is 17 times 4?”). If the SQL got better and ordinary answers collapsed, that is catastrophic forgetting: the new training overwrote useful behaviour. Overfitting is the narrower case where training examples are memorized and the holdout gets worse. Signs: training loss near zero, holdout SQL that only works on questions copied from the training file, or nonsense on anything else. Responses: fewer epochs, a smaller learning rate, more varied examples, and a handful of ordinary chat examples mixed in.

    TRL can also attach LoRA without Unsloth, via peft_config=LoraConfig(r=16, lora_alpha=16, target_modules="all-linear") on SFTTrainer. If you instead fine-tune a custom-license model from the model cards (Kimi, Hy4, MiniMax, and others), that model’s license is the one that applies. Do not relabel it Apache 2.0.

3. Training from scratch

Pretraining starts from random weights and predicts the next token across a huge text collection. There are no question-and-answer pairs. The model’s knowledge is whatever patterns that prediction carved into the weights.

A tokenizer is the program that turns text into token ids and back. The Shakespeare exercise below uses a character tokenizer: one character, one id, a vocabulary of a few dozen symbols. Qwen and GPT-2 use a byte-pair tokenizer: frequent character sequences are merged into single tokens. You cannot take weights trained with one tokenizer and feed them ids from another. The ids would mean different pieces of text.

Basic What “from scratch” costs

A widely used planning rule, from the Chinchilla paper (Hoffmann et al., 2022), is on the order of 20 training tokens per parameter. A 7-billion-parameter model then wants on the order of 100 billion tokens. That is a cluster, a prepared corpus, and a bill measured in many GPU-days. Frontier runs are larger still: trillions of tokens. This page does not quote a dollar total for those runs, because a serious figure needs a named cluster price and a named token count, and those vary by lab.

What you can run yourself is a toy. Andrej Karpathy’s nanoGPT trains a 6-layer GPT on the tiny Shakespeare file (about 1 MB). His README says that config takes about 3 minutes on one A100 and reaches a validation loss around 1.47, and that a smaller CPU run takes about 3 minutes with a worse loss around 1.88. The same README says reproducing GPT-2 (124M) on OpenWebText takes about 4 days on one 8×A100 40GB node. In November 2025 he marked nanoGPT as old and pointed people at nanochat. The Shakespeare recipe is still the small, readable one, so it is the exercise here.

Continued pretraining is the middle ground. You start from weights that already exist and keep doing next-token prediction on your own text (manuals, code, papers), still without chat labels. nanoGPT’s train.py accepts --init_from=gpt2 (also gpt2-medium, gpt2-large, gpt2-xl) for that idea, but only with a dataset that uses the GPT-2 tokenizer. The character-level Shakespeare config is not that dataset. Do not point --init_from=gpt2 at train_shakespeare_char.py.

Detailed Tiny GPT, step by step

  1. Clone the repository and prepare the character-level data. prepare.py downloads the tiny Shakespeare file if it is not already there (it uses requests), builds a character vocabulary, and writes train.bin and val.bin. The larger GPT-2 reproduction in the same README needs more packages; this path does not. 
    git clone https://github.com/karpathy/nanoGPT
cd nanoGPT
pip install torch numpy requests
python data/shakespeare_char/prepare.py
  2. Train. On a GPU, including a Colab T4 runtime: 
    python train.py config/train_shakespeare_char.py

    That config, from the repository, is a 6-layer, 6-head model, 384 feature channels, context of 256 characters, learning rate 1e-3, 5,000 iterations. Checkpoints go to out-shakespeare-char.

  3. On a laptop CPU, use the smaller command from the README. --device=cpu and --compile=False are required there: 
    python train.py config/train_shakespeare_char.py --device=cpu --compile=False --eval_iters=20 --log_interval=1 --block_size=64 --batch_size=12 --n_layer=4 --n_head=4 --n_embd=128 --max_iters=2000 --lr_decay_iters=2000 --dropout=0.0
  4. Sample text from the checkpoint: 
    python sample.py --out_dir=out-shakespeare-char
# CPU:
python sample.py --out_dir=out-shakespeare-char --device=cpu
  5. Read model.py while it trains. It is a small GPT: tokens go in, a stack of attention layers mixes them, and the model predicts a distribution over the next character. The loss is how surprised it was by the actual next character. That is the whole of pretraining, at a size you can see.
  6. If you later try continued pretraining, use a GPT-2-tokenized dataset and --init_from=gpt2, as train.py documents. Keep the Shakespeare character run as the from-scratch lesson.

Roadmap for a beginner

One thread: a single known schema, then notes, then a small fine-tune, then a look at real pretraining. Stop when the holdout SQL is good enough. You do not need all eight weeks to be useful.

  1. Week 1. Install Ollama and run one model from the install section. Ask it for a DuckDB SELECT against a schema you paste by hand. Run the SQL yourself and compare.
  2. Week 2. Put three short notes through rag_docs.py. Change a sentence in a note, re-run the upsert, and see the answer change. That is the point of RAG.
  3. Week 3. Load one real CSV with DuckDB’s read_csv and use sql_sandbox.py. Keep the connection read-only.
  4. Week 4. Write 40 to 80 text-to-SQL lines for that one schema. Run every statement. Move about one in five questions to holdout.jsonl.
  5. Week 5. Run the QLoRA script on a free Colab T4 or a 24 GB card. Compare base and tuned models by executing SQL, not by reading the loss alone.
  6. Week 6. Export q4_k_m, ollama create, and write the model card. Include the Apache 2.0 license if the base model is Qwen2.5.
  7. Week 7. Clone nanoGPT and train the Shakespeare character model. Read model.py. Notice that this did not teach SQL.
  8. Week 8. Decide. If your holdout questions are about changing documents or tables, invest in RAG and the SQL sandbox. If the model still refuses to emit clean SQL, add checked examples and fine-tune again. Do not start a pretraining run to fix either problem.

Glossary

Short definitions for the words used above. The first time each word appears in the guide, the sentence there is the definition that counts.

Token
A piece of text the model treats as one step. Often smaller than a word. Different tokenizers split the same sentence differently.
Tokenizer
The program that converts text to token ids and ids back to text. Weights only make sense with the tokenizer they were trained with.
Context window
The maximum number of tokens in one request, including the prompt and the answer being written.
Prompt
The text you send to the model for one request.
Inference
Using a trained model to produce text. No weights have to change.
Weight
One stored number inside the model. The file you download is the full set of weights.
Parameter
A weight the training process was allowed to set. “7B” means about 7 billion of them.
Embedding
A list of numbers that represents a piece of text, used so that similar texts land near each other.
Vector database
A store that keeps embeddings and returns the closest ones to a new embedding. Chroma, FAISS, and pgvector are three options in this guide.
Chunking
Cutting a document into pieces that fit an embedding model and a prompt. Overlap keeps a sentence from being sliced with no intact copy.
Retrieval
The search that returns those nearby chunks.
RAG
Retrieval-augmented generation: retrieve chunks, put them in the prompt, then generate an answer. The weights stay as they were.
Sandbox
A restricted place to run code the model wrote. Read-only database access, no network, and a timeout are the useful restrictions.
Schema
The column names and types of a table. It is what the model needs to write SQL. It is not the rows.
Fine-tuning
More training on a model that already has weights, so that behaviour changes. In this guide it is supervised: each example has a target answer.
LoRA
Low-rank adaptation. Small matrices are added and trained; the original weights stay frozen.
Rank
The width of those LoRA matrices. The script uses r=16.
QLoRA
LoRA while the frozen base weights are loaded in 4-bit quantization.
Quantization
Storing weights in fewer bits. Smaller and faster, with some loss of accuracy. q4_k_m is one 4-bit GGUF recipe.
GGUF
A file format llama.cpp and Ollama use to load a quantized model.
Epoch
One full pass over the training examples. The script uses 2.
Learning rate
How large each weight update is. The script uses 2e-4 (0.0002) for QLoRA.
Loss
A number that is lower when predictions match the training targets. It is not a substitute for running the SQL.
Checkpoint
Weights saved at a point in training so you can resume or compare.
Holdout
Examples you never train on, used once to see if the model works on questions it has not memorized.
Overfitting
Training performance keeps improving while holdout performance gets worse. The model has memorized the training set.
Catastrophic forgetting
The new task works, and older skills the base model had no longer work.
Pretraining
The first training run: next-token prediction on a large corpus, starting from random weights.
Continued pretraining
Next-token prediction that starts from existing weights and a new corpus, without chat labels.
Chat template
The exact wrapping of system, user, and assistant turns. Training and Ollama must use the same one.
Modelfile
Ollama’s text file that names a GGUF (or another base model) and the parameters and template used to create a local model.
Adapter
The small set of trained LoRA matrices, saved separately from the base model. lora_adapter in the script.
Base model
The model you start from. Here, Qwen2.5-7B-Instruct in a 4-bit Unsloth build.
